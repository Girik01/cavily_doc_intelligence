Documentation intelligence: architecture and validation note

Assignment 2 · demonstrated on the Cavli C16QS (LTE Cat 1bis) · Python, FastAPI, Qdrant Cloud, OpenAI gpt-5.5 + text-embedding-3-small, BM25 · local prototype

1. Sources and what is not available

The system starts empty. The user supplies public links (PDFs or web pages) and PDF files; nothing about a product is built into the code. For the demonstration (docs/demo_sources.md) the following were supplied:

C16QS product page, LTE Cat 1bis category page, C-Series FAQ (cavliwireless.com)HTML1 each; no revision or date stated. The FAQ answers are read from the page data (one passage per question).

C16QS Technical Specification DocumentPDF, 8 and 6 pagesV2.0 (distributor mc-technologies.com; PDF created 2023-11-08) and V2.9 (distributor endrich.com; PDF created 2025-03-21)

Disclosures. The specification PDFs are third-party distributor copies; Cavli's own site does not publish them. The PDFs state no version: the labels V2.0 and V2.9 are typed by the uploader (taken from the file names) and the system never guesses a version. The brochure (form-gated) and the hardware and AT command manuals (customer-portal login) are not accessible and are not used; the user can list them in an optional box so that "not verified" answers name them.

3. Source updates and re-indexing

  • Ingestion (Sources tab, repeatable): links and files are processed in one background job. For every copy the system stores title, URL, document type, host, fetch time, SHA-256 (HTML is hashed on its visible text because raw HTML changes on every request), revision and dates only if the document states them (otherwise "none stated"), and the PDF facts it contains. "Fetch again and re-index" downloads every added link again; a new hash becomes a new version, the old one is marked superseded but kept for audit and hidden from default answers. Uploaded files have no link and are not re-downloaded.
  • Newer version (Sources tab): the user chooses a document and uploads a PDF or pastes a link. Identical content is refused. The previous current version becomes superseded, the new one is indexed, and a What changed table lists facts before and after: a model summarises the line diff and code keeps only values that occur in the old or the new text. No version is simulated; both files are real.
  • Expert review: conflicts between documents are found by a model that judges the 30 most similar passage pairs from different documents; its quotes must exist word for word in both passages, otherwise the finding is dropped. Other items: outdated versions, documents with no revision or date, uploaded files without a public origin. Each item quotes both sides. A named person records a decision or reopens it; nothing is resolved by the AI. Open items are given to the answer model as unresolved issues. The tab shows which items a user's question ran into.

4. Retrieval, citations and accuracy controls

  • Retrieval: dense (text-embedding-3-small in Qdrant) plus keyword (BM25), fused by reciprocal rank, top 8 passages; mode selectable; retrieved passages with ranks are shown. Web pages are split by heading, FAQs by question, short PDFs by page, long technical PDFs with a layout-aware reader that rebuilds table rows and columns from word positions.
  • Citations: PDF passages cite the real page; web passages cite the section name or FAQ question; no page number is invented for HTML. Each citation shows title, location, revision or date note, URL and the supporting passage.
  • Checks: cited labels must exist; every number in the answer must occur in the cited text; otherwise "Not verified". Questions no document answers are refused and name any documents the user listed as not accessible. Ambiguous questions get an answer per case plus one clarifying question. Passages and questions are untrusted text in the prompt.
  • Known gap: the check covers numbers, not names, and compares them with all cited passages together, not with the passage cited for each statement. The conflict judge compares only the 30 most similar pairs, so it can miss conflicts. Per-statement verification is described, not built.

5. Validation results

The evaluation is generated from the documents that are loaded, so it keeps working when the sources change: the model writes about ten questions from sampled passages (code keeps a question only if its expected fact occurs verbatim in that passage; a fact counts as present when each word and number of it is in the answer), and two unanswerable questions are added. Each question runs through the same code as the chat and is graded for expected fact, expected document cited, citation validity and failure category; the failure report and documentation recommendations are written from that run's evidence.

Demonstration run (5 documents, V2.0 then V2.9 of the specification; output in docs/sample_run/): 12 of 12 passed (10 answerable, 2 unanswerable). The same flow gave the sleep-mode current as "TBD" (V2.0, page 5) before the upgrade and 11 µA (V2.9, page 4) after it, and 7 review items (4 conflicts such as the number of variants and the GNSS constellations, one change list of 15 differences between V2.0 and V2.9, missing dates, uploaded-file provenance). An earlier run of this generator produced 1 failure (the grading rule was too strict about "3xUART" versus "3 UART") and was fixed; this is recorded, not hidden.

Limits of this evidence: the questions are written by the model from the same documents the system answers from, so 12/12 shows the pipeline works end to end and is not proof of general accuracy. An earlier author-written 25-question evaluation of the original C16QS set (22 of 25; failures were citations of review items instead of PDF pages and one borderline ambiguity question) is kept in eval/ as evidence.

6. Security, privacy, costs, limits

  • Security: OpenAI and Qdrant keys only in .env (git-ignored, none in the repository). Only links the user supplies are fetched; no login, form or personal data was used. The web interface runs locally (127.0.0.1) and has no user accounts. Downloaded files are not committed. Uploads are checked to be PDFs by their bytes; links must be http(s) and return a PDF or a web page.
  • Models, services and costs: OpenAI gpt-5.5 (reasoning off) for answers, conflict judging, change summaries and evaluation generation; text-embedding-3-small for embeddings; Qdrant Cloud as vector store; BM25 runs locally. Measured on 6 questions: about 5,100 input and 220 output tokens per answer plus one small embedding call. A processing run adds up to 30 short judging calls (cached). Money cost = tokens x the current OpenAI price, which this note does not state because prices were not checked.
  • Assumptions: the documents the user supplies are genuine; version labels are the uploader's. Simulated: nothing. Not built: scheduled re-indexing (it runs when the button is pressed), per-statement citation verification, user accounts, uploads other than PDF.
  • Human approval: nothing is published or sent automatically; review items need a named expert decision, and any use of answers outside the team needs human approval first.
  • Limits: version order rests on what the uploader says (and file dates); one run per question (wording varies); generated questions cannot support general accuracy claims; a document of another type may need a better reader than the generic one.
